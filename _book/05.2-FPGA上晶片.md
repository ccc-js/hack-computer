# 5.2 FPGA 上晶片：344 LUT4＋48 DFF 與 22 MHz

## 從網表到晶面

第 5.1 節的產出（344 LUT4 + 48 DFF = 392 cells）交給 `MicroPnR`：
佈局（SA 退火）→ 繞線（曼哈頓通道）→ STA。實跑結果全表：

```js
// node 直跑 MicroPnR().run(netlist).stats
{
  totalCells: 392,
  lutCount: 344,
  dffCount: 48,
  gridArea: 676,        // 26×26
  density: "0.58",      // 60% 利用率目標下的實際密度
  totalWireLength: 4166,   // SA 有隨機性，每次跑約 3,900–4,200
  criticalPathNs: "45.55",
  fmaxMHz: "22.0"
}
```

| 階段 | 結果 | 對應理論 |
|---|---|---|
| 網格 sizing | $\lceil\sqrt{392/0.6}\rceil = 26$ | 60% 利用率的經驗法則 |
| 佈局 | HPWL 總計約 4,100 單位（SA 隨機，每次略異） | SA 退火（3.2 節） |
| 繞線 | 曼哈頓 L 形、每通道 6 tracks | Lee 1961（3.3 節） |
| STA | 45.55 ns → **22.0 MHz** | DAG 最長路（4.1 節） |

## 網格為什麼是 26×26

```js
const gridSize = Math.max(4, Math.ceil(Math.sqrt(totalCells / 0.6)));
// 392 / 0.6 = 653 → sqrt = 25.6 → 26
```

利用率 0.6 是 FPGA 工具的經典預設：留 40% 空隙給繞線資源。
擠到 0.9，線長會因擁塞暴增（繞線是二次效應）；放到 0.3，浪費面積。
本專案直接寫死 0.6——一個被工業界驗證過的甜點值。

## 關鍵路徑在 45.55 ns 裡

45.55 ns ÷ 1.2 ns/LUT ≈ **38 級邏輯**（含線延遲攤薄）。這條路大概率是：

```text
DFF(launch) → ALU 深度組合邏輯（進位鏈＋選擇樹）→ 寫回 mux → DFF(capture)
```

Hack CPU 的資料通路裡，一拍內要做完「讀暫存器 → ALU 運算（16-bit 進位傳播）→
寫回選擇」，ALU 的進位鏈是天然長路。**22 MHz 對 38 級的未優化電路是合理成績**；
真實工具會用 retiming（跨 DFF 移動邏輯）或二級管線把它切半。

## 時序數據的回饋價值

22 MHz 這個數字回答了 Nand2Tetris 課程留白的最後一問：
「我的 CPU 真的能做進 FPGA 嗎？跑多快？」——**能，而且很慢**。
慢的原因不是 Hack 指令集，而是：

1. 單週期架構（一拍做完取指到寫回）→ 38 級長路（架構層原因）；
2. 未做時序驅動佈局（工具層原因）；
3. 經驗延遲模型較粗（模型層原因）。

三層原因各自可修——這正是第 4.3 節「回饋上游」清單的案例化。
