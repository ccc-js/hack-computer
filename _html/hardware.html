1. 硬體線是什麼？

Nand2Tetris 的前半程（projects 01–05）是用 HDL 疊出一台電腦：從 Nand 拼出閘、加法器、ALU、暫存器、記憶體，最後拼出 CPU。本系統把「教科書上的模擬器」重新寫成 JavaScript 工具鏈（cli/hdl2js.js），每個 .hdl 都即時編譯成可執行的 JS 類別，.tst 測負責驗證。

「一條硬體線」的價值：你寫的 PC.hdl、ALU.hdl 不只是課本交代版，它們在本系統裡真的能跑——被 hdl2js 編譯、被 .tst 驅動 tick/tock，甚至 PC 的偵錯探針讀出那些 RISC-V 指令的執行結果。

這本書講三件事：邏輯（閘、組合 vs 時序）、工具（hdl2js ＋ .tst）、旅程（01→05 的疊法與本目錄自研 CPU）。

2. 全流程總覽

.hdl（電路稿） → parseHdl : 文字 → AST（chip 名、腳位、parts） → elab / lib : 晶片庫＋實例樹＋Builtin 原語 → codegen (hdl2js): 每顆晶片 → 一個 JS 類別（零件實例＋對位連線） → .tst → run() : 輸入腳位取樣、tick/tock 時脈、輸出與 .cmp 比對 → 通過（綠燈）＝此 .hdl 真的按規格工作 ✔ 第三支路（本目錄自研）：Riscv32i/rv32i.hdl —— 用同一條 HDL 模擬線跑整顆 RV32I CPU。

3. HDL 的本質

HDL 不是程式，是接線圖的文字形式：PARTS 每一行是一個實例與它的接線（pin=運算式）。關鍵觀念：

  • eval 順序由硬體自身決定：elab 依「先有輸入才可算輸出」排出 evalOrder（拓撲序），不依抄寫順序。
  • slice 逐位元：out[0..7]、in[8..15] 綁定到 per-bit 的 Wire。
  • 多重輸出動作規則：同一 net 被多個 part 寫 → 語法錯；同一 part 輸出綁兩條線 → alias。
third_party/courses/01/Mux8Way16.hdl（摘錄）
CHIP Mux8Way16 {
    IN  in[16], sel[3];
    OUT out[16];
    PARTS:
    Mux4Way16(a=a, b=b, c=c, d=d, sel=sel[0..1], out=r0);  // …8 路
    Mux16(a=r0, b=r1, sel=sel[2], out=out);               // 2 段式選擇
}

▲ 兩段式 8 路 Mux：不是「開關陣列」，而是樹狀組合——HDL 的每行都是真硬體的形狀。

💡 動手看：../dist/hdl.html#case=../01/Mux8Way16 → 想看這些實例接什麼，切「檢視電路圖」逐層點入（Mux8Way16 → Mux4Way16 → Mux16 → Nand）。

4. 組合邏輯與 eval()

組合邏輯的特點：輸入一變，輸出立刻重算——沒有記憶。hdl2js 為每個晶片生成的 eval() 就是「依 evalOrder 逐(part) 呼叫子 eval」。

lib/hdl/codegen.js — 生成的 eval() 形狀（概念摘錄）
eval(inputs) {
  // TOP: 每個 child 實例一份
  const c0 = new Mux();         // ← 子實例
  c0.set('a', va); c0.set('sel', vsel);
  c0.eval();                     // ← 子先算
  this.set('out', c0.pop('out')); // ← 父收結果
}

▲ 生成式 eval 由父往子推、子往父收；每個 part 只有「先取 sample、再 eval」一種模式（組合）。

檢查點：Add16 的 16 bit 全在「同一 eval」完成；時間在組合世界是卻不存在的——除非你畫 STA 圖（那是 EDA 書第 7 章的事）。

5. 時序邏輯與 tick/tock

時序元件（DFF、Register）引入「狀態」和「時脈」。本系統的模型來自 Nand2Tetris 原教科書的 tick/tock：

  • eval 前取樣：時序元件在 eval 讀的是舊狀態（out(t)），不會立刻吃到新輸入。
  • tick()：時鐘上升 → latch（回收同時說「我要記住現在輸入」）。
  • tock()：時鐘下降 → q = latch（新狀態總出可見）。
lib/hdl/codegen.js — DFF 生成（摘錄）
// bit 位元級 DFF：eval() 讀舊值；tick() 收 latch；tock() 公佈 q
tock() { this.q = this.latch; }
tick() { this.latch = this._get('in'); }

▲ 生成式時序元件都有 {latch, q} 兩段式狀態；從 Bit 這顆 1-bit 例子手寫的高階晶片（如 PC）就會真的感覺到「下一次 eval 前不吃新輸入」的規則。

💡 動手看：../dist/hdl.html#case=../03/a/Register → 主面板會逐 tick/tock 跑 .tst；load=1 的那個 tock 之後才看得到 out 改變。

6. hdl2js：讓 HDL 變 JS

CLI node cli/hdl2js.js --dir DIR [--test F.tst] 是硬體線主入口：讀一串 .hdl → elab 全庫 → codegen 出成包 JS → 若指定 .tst 就直接 run 比對 .cmp。本書把 codegen 三段重要規則整理：

規則生成物在意義上
evalOrder 拓撲列子 eval 依序被呼叫等價組合邏輯的「資料流」
時序元件 special-casetick/tock/latch把「時脈驅動」的狀態機規則化
slice 逐位別名細粒度 Wire 引用支援 in[3] 這種前面文化
lib/hdl/codegen.js — part 待判（摘錄）
// part 是否為有狀態（clocked）：eval 輸出取自狀態、輸入在 tick 才取樣
isClocked(chip) → { cpuRoute: 'latch', nextEval: 'eval 取舊值' }

▲ codegen 的兩世界差別就這麼一句：有狀態 vs 無狀態、決定生成 eval 的樣板。

⚠ Memory.tst（鍵盤互動測資）需要人工按鍵，CLI 自動跳過；這是課程原測資的「互動驗收」設計，不是 bug。

7. .tst 測資與 run()

.tst 是一種簡易腳本：set 輸入↦ tick/tock↦ output。工法上和硬體模擬激烈不同——它是把硬體當黑盒驅動，與 .cmp 逐行比對。

third_party/courses/03/a/Register.tst（摘錄）
set in -32123,
set load 0,
tick, output;    // ↑ 從舊狀態讀 out
tock, output;    // ↑ 遇 load=1 的 tick 之後，out 才改
set in 12345,
set load 1,
tick, output;  …
lib/rt/tst.js — run() 的節奏（概念）
for (const step of script.steps) {
  set_inputs(step.sets);
  if (step.tick) model.tick();   // 升 → latch
  if (step.tock) model.tock();   // 降 → q=latch
  if (step.output) out(model, step.output);
}

▲ run() 是「驅動硬體」的 compiler：set/tick/tock/output 四種操作重覆展開成實際的 JS 呼叫。

💡 動手看：../dist/hdl.html#case=../03/a/Register 主面板會跑這支 .tst；只要改壞 .hdl 就會立即 fail（常見錯因是 off by one tick）。

9. 自研 CPU：Riscv32i

Riscv32i/rv32i.hdl 是本目錄自研的單週期 RV32I CPU（word 定址；資料通路五段一次做完的單週期設計）。它 就是第 8 章=cycle 技術的成果展示：

Riscv32i/rv32i.hdl — 資料通路摘錄
//   IF：PC（R32）→ ROM32 取指；pcSeq＝pc＋1；pcTgt＝pc＋imm。
//   ID：RvDec 解碼（rd/rs1/rs2/imm/ctl）；RF32 讀 r1/r2（a3＝dbgRd 供除錯）。
//   EX：A 選（r1/imm/pc）× B 選（r2/imm）→ RvAlu；RvBr 判分支；
//       JALR 目標＝r1＋imm（word 定址不斷 LSB）。
//   MEM：RAM32W（SW 寫 r2；位址取 aluY[14:0]）。
//   WB：aluY / memOut / pcSeq（JAL/JALR link）三選一。
CHIP rv32i {
    IN  dbgRd[5];
    OUT pc[32], dbgReg[32];
    PARTS:
    // IF
    R32(in=pcNext, load=pcLoad, out=pc);
    ROM32(address=pc[0..14], out=instr);
    Add32c(a=pc, b=one, cin=false, out=pcSeq);
    // ID / EX / MEM / WB …（完整實作在 rv32i.hdl）
}

▲ 一週期一指令：五段都貼在同一 eval 一次做完；附帶 dbgRd/dbgReg 除錯面板（dbgRd/dbgReg 探針）讓 rv32i.tst 能按位讀狀態。

支援指令範圍
R 型add/sub/sll/slt/sltu/xor/srl/sra/or/and（10 種全）
I 型addi/slli/srli/srai/slti/sltiu/xori/ori/andi
載存LW / SW（word 定址）
跳轉LUI / AUIPC / JAL / JALR
分支beq / bne / blt / bge / bltu / bgeu
停機HALT（opcode 1111111：黏住 halted、凍結 pc）

11. 小測驗

Q1. HDL 為什麼「不按行順序」也能對出正確的 eval 順序？
✔ A。elab 按「先有輸入才可算輸出」排 evalOrder；抄寫順序無意義。
Q2. DFF 的 tock() 在生成的 JS 裡做什麼？
✔ B。{latch, q} 是時序元件的兩段式；tick 收樣本、tock 公佈。
Q3. .tst 檔的迴圈結構裡，多數理論架構中「tick」實際觸發的是？
✔ B。tick 是時脈上升：時序元件把輸入 latch 進去；tock 下降，才公佈 q。
Q4. rv32i 的 word 定址簡化，放棄了哪些「真 RV32」的行為？
✔ A。word 定址省了 LB/LH/LBU/LHU/SB/SH 與未對齊；word 定址 jump 目標不斷 LSB（同 RV32S 的簡化）。

12. 名詞表

HDL
描述接線圖的文字（本系統吃 Nand2Tetris 課程版）；不是程式。
elab
把「一堆 .hdl」整理為晶片庫＋實例樹；elab 之後才有 evalOrder。
codegen
把晶片生為 JS 類別；hdl2js 主要工作。
tick / tock
時脈上升／下降兩段；時序元件的 latch 與 q 公佈時機。
.tst / .cmp
測資腳本與黃金答案；run() 驅動硬體後逐行比對。
slice
in[3..7] 型的位元段；以 per-bit Wire 結合。
dbgRd / dbgReg
rv32i 的除錯探針：選讀其任一暫存器（不用硬體新品管中人工真值）。
word 定址
本目錄 CPU 的記憶體簡化；「1 地址 = 1 word」。
